# issue-add — やることをIssueにする

Issueを立てただけで終わらせない。**Projectに載せ、優先度をつけ、依存を張るまでが1セット**。
盤に載っていないIssueは `issue-run` から見えず、永久に着手されない。

## 1. 粒度を決める

**1 Issue = 1 PR = 1つの完成した成果物。**

| 良い | 悪い |
|---|---|
| Threads自動投稿を実装する | SNS自動化 |
| docsをv3方針に全面改訂する | ドキュメント整理 |
| プロフィールアクセス率を fetch_metrics に追加する | 計測をなんとかする |

大きすぎるものは分割し、親を `blocked by` 子で繋ぐ。
「〜を検討する」で終わるものはIssueにしない。**何が出来上がったら閉じられるか**を書けないなら、まだIssueにする段階ではない。

## 2. 本文を書く

```markdown
## 目的
なぜやるのか。どのドキュメントの、どの判断に効くのか（docs/へのリンク）。

## 成果物
終わったときに存在しているもの。ファイル名・コマンド・数値で書く。

## 完了条件
- [ ] 検証可能な条件を並べる（「動くこと」ではなく「このコマンドが通ること」）

## 依存
先行: #12（〜が終わっていないと着手できない理由）
後続: #20
```

完了条件は**他人が見て○×を付けられる**粒度にする。ここが曖昧なIssueは
`issue-run` が「終わったつもり」でマージしてしまう。

## 3. 立てる

```bash
gh issue create \
  --title "[領域] やること" \
  --body-file /tmp/body.md \
  --label pipeline \
  --milestone "Phase 1: 検証"
```

タイトルは `[領域] 動詞で終わる一文`。領域は `準備` `実装` `運用` `判断` `調査` から選ぶ。

| ラベル | 使いどころ |
|---|---|
| `harness` | Issue運用・開発の仕組みそのもの |
| `documentation` | docs / README |
| `pipeline` | 動画生成パイプライン |
| `publish` | 各SNSへの投稿 |
| `metrics` | 計測・レポート |
| `decision` | **数字を見て人が決める**（自動実行しない） |
| `manual` | **本人しかできない**（自動実行しない） |

`decision` と `manual` は `issue-run --auto` から除外される。
自動で回せないものにこのラベルを付け忘れると、ループが手を出して壊す。

## 4. 盤に載せる

```bash
python3 tools/gh_board.py add 23 --priority P1 --status Todo --iteration Current
```

| 優先度 | 意味 |
|---|---|
| `P0` | これが終わらないと他の判断が全部ずれる |
| `P1` | 今のフェーズの本体 |
| `P2` | 今のフェーズ内だが、後ろでよい |
| `P3` | 次のフェーズ以降 |

優先度は**締切ではなく依存の深さ**で決める。多くのIssueをブロックしているものほど上。

## 5. 依存を張る

```bash
python3 tools/gh_board.py block 30 --by 23,24   # 30 は 23 と 24 を待つ
```

GitHub公式の依存関係API（`/issues/{n}/dependencies/blocked_by`）を使う。
**本文に「Blocked by #23」と書くだけでは駄目**。ただの文字列で、ブロック判定に使えない。

依存は「無いと物理的に着手できない」ときだけ張る。
「順番としてはこっちが先が自然」程度なら優先度で表現する。張りすぎると盤が動かなくなる。

## 6. 確認して報告する

```bash
python3 tools/gh_board.py list
```

`🔒` が待ち、`👤` が人手待ち。**P0が全部 🔒 になっていたら依存の張り方を間違えている**（先頭が動かない）。

報告は、立てたIssue番号・優先度・依存の連鎖を1つの表で示す。
