# 08. 自動化方針とセットアップ

> 最終更新: 2026-07-26 ／ 前提: [06_KPI・運用.md](./06_KPI・運用.md)（計測項目とレビュー手順）、[01_市場分析.md](./01_市場分析.md)（PF仕様）

## 1. 方針 — 何を自動化し、何を自動化しないか

伸びの本体（演奏・編集・冒頭0〜3秒の設計・投稿直後の交流）は自動化できない。自動化が効くのは**投稿・計測・企画の周辺作業**だけで、目的は「浮いた時間を制作に戻すこと」と「継続断絶を防ぐこと」。

| レイヤー | 自動化 | 理由 |
|---|---|---|
| 計測・記録 | **する（最優先）** | 週次レビュー30分のうち10分が数値記録。ここが継続断絶の主因（06の4章）。かつ蓄積データが横串C-1「0→1,000の全数値公開」やピラーB（AI分析）の素材そのものになる |
| 投稿 | する（PF次第・3章） | まとめ撮り→予約投稿で「週0本」を防ぐ。ただしTikTokは実質不可 |
| 企画・台本の下書き | 半自動 | トレンド定点観測（05の4章）と3面分のキャプション生成 |
| 演奏・撮影・編集 | **しない** | ここが価値の源泉。浮いた時間を全部ここに使う |
| フォロー・いいね・コメント | **絶対にしない（2章）** | 規約違反。凍結リスク |

## 2. やってはいけない自動化（リスク管理に追加）

**自動フォロー／自動いいね／自動DM／フォロワー・再生数の購入は3PFすべてで規約違反**。シャドウバン・アカウント凍結の対象で、Phase 1の検証データも汚染される（数値が実力を反映しなくなり、ピラーA/Bのフォーマット優劣の判定＝Phase 1の最重要目標が不能になる）。「SNS自動化ツール」として流通しているものの多くがこれに該当するため、導入前に必ず「何を自動でやるツールか」を確認する。

**投稿直後30〜60分のコメント返信は手動で行う**。ここは自動化しないことがアルゴリズム上も有利に働く。

## 3. プラットフォーム別の自動化可否

| PF | 自動投稿 | 自動計測 | 制約 |
|---|---|---|---|
| **Threads** | ○ | ○ **実装済** | Threads API。3PFで最もハードルが低い |
| **Instagram** | ○ | ○ **実装済** | **プロアカウント（ビジネス/クリエイター）必須**。動画は公開URLにホストが必要。API経由のReelsは5〜90秒（アプリは3分まで可）。24時間あたり100投稿まで |
| **YouTube Shorts** | ○ | 未実装 | YouTube Data API。無料クォータで1日6本程度＝十分 |
| **TikTok** | **✗ 実質不可** | ✗ | Content Posting APIは審査（audit）必須。**未審査だと投稿がSELF_ONLY（本人しか見えない）＋アカウントを非公開に設定する必要**があり、サーバー側で強制されるため回避不可 |

**TikTokの運用**: Web版の予約投稿機能に手動でキューを積む（月1回10分）。数値は各投稿のアナリティクスから週次CSVに手入力する。TikTokは0フォロワーでもバズり得る主戦場（06の2章）なので、手動コストを払う価値がある。

## 4. 計測の自動化（実装済み）

### 4-1. 何ができるか

```
python3 tools/fetch_metrics.py       # Threads/IGのインサイトを取得 → data/YYYY-Www.csv を作成・更新
python3 tools/weekly_report.py       # 週次CSV → レビュー用Markdownを生成
python3 tools/weekly_report.py --issue 42   # レポートをGitHub Issue #42 にコメント
```

- 手入力列（`pillar` / `issue_no` / `completion_rate` / `follows_gained` / `hypothesis` / `result_note`）は**APIの値で上書きされない**。人が書いた文脈は消えない
- `views_48h`（初速）は**投稿から48時間以内に実行したときだけ**記録され、以後は上書きしない
- レポートは北極星3指標（保存率・完走率・**コメント率**）とピラーA/B比較を先頭に出す。
  コメント率はトーク型（ピラーA）の主指標（06の1章）
- レポートには「手入力が必要な項目」のチェックリストが自動で付く
- `pillar` 列に入れる値は `sakanaction`（A）/ `datalab`（B）。06の6章のラベル定義に合わせる

### 4-2. トークンの準備（初回のみ）

いずれも [Meta for Developers](https://developers.facebook.com/) でアプリを1つ作り、そこに両方のAPIを追加するのが早い。取得した**長期トークン**を `~/dev/.cowork-secrets/` に置く（**リポジトリにコミットしないこと**）。

**Threads**（参照: [Threads API](https://developers.facebook.com/docs/threads)）

1. アプリに「Threads API」ユースケースを追加し、`threads_basic` と `threads_manage_insights` を許可
2. 自分のThreadsアカウントを連携して短期トークンを取得
3. 長期トークン（60日）に交換: `GET https://graph.threads.net/access_token?grant_type=th_exchange_token&client_secret=<秘密鍵>&access_token=<短期トークン>`
4. `~/dev/.cowork-secrets/threads_token.txt` に保存

**Instagram**（参照: [Instagram Platform](https://developers.facebook.com/docs/instagram-platform)）

1. **Instagramをプロアカウント（ビジネスまたはクリエイター）に切り替える**（未切替だとAPIが一切使えない）
2. アプリに「Instagram」プロダクトを追加し、Business Login for Instagram を設定。`instagram_business_basic` と `instagram_business_manage_insights` を許可
3. 長期トークンに交換: `GET https://graph.instagram.com/access_token?grant_type=ig_exchange_token&client_secret=<秘密鍵>&access_token=<短期トークン>`
4. `~/dev/.cowork-secrets/ig_token.txt` に保存（ユーザーIDを明示したい場合は `ig_user_id.txt` も。未設定なら `me` を使う）

### 4-3. トークンの失効対策（重要）

長期トークンは**60日で失効する**。放置すると自動計測が静かに止まるため、月1回延長する:

```bash
python3 tools/fetch_metrics.py --refresh-token
```

ファイルから読んでいる場合は新しいトークンが自動で保存される。

### 4-4. 定期実行

週次レビュー（毎週日曜）の直前に流す。`crontab -e` に追加:

```cron
# 毎週日曜19:50 に計測 → レポートをIssueにコメント（Issue番号は週次レビュー用Issueに合わせる）
50 19 * * 0 cd ~/repo/bashaka/biz/personal-sns-operation && /usr/bin/python3 tools/fetch_metrics.py >> /tmp/sns_metrics.log 2>&1
# 毎月1日にトークン延長（60日失効対策）
0 9 1 * * cd ~/repo/bashaka/biz/personal-sns-operation && /usr/bin/python3 tools/fetch_metrics.py --refresh-token >> /tmp/sns_metrics.log 2>&1
```

投稿の初速（48時間以内の再生数）を取りこぼしたくない場合は、日次実行にしてもよい（`0 21 * * *`）。

## 6. このドキュメントの更新ルール

- PFのAPI仕様は頻繁に変わる（特にMetaのmetric名）。**計測が壊れたら3章の表とスクリプトを更新してコミットする**
- `tools/fetch_metrics.py` はmetric取得に自動フォールバックを入れてあり、一部metricが廃止されても取れる分だけ記録して動き続ける。ただし列が空になり続けている場合は仕様変更を疑う
